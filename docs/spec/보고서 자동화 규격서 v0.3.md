- v0.2 변경 요약(2026-11-12): 최종 산출물 DOCX 원본 + PDF 변환, 데이터는 팀원이 도구를 수동 사용하여 정리·제출, 블루팀 보고서 버전 0.5/1.0, 블루팀 신규 데이터 9종(3-13\~3-21) 추가. 변경 위치 전체는 8장 참조

## 1. 개요

### 1-1. 목적

- 보고서 양식 3종을 「데이터 + 규칙」으로 분리하여, 작성자가 바뀌어도 동일한 품질의 보고서를 생성하는 것을 목표로 함
- 표·수치는 데이터에서 자동 생성하고, 서술은 사람이 최대한 작성하며 AI는 규칙에 따라 다듬거나(문체·길이·용어) 정해진 일부 필드만 작성함. 검증 규칙으로 최종 품질을 확인함

### 1-2. 대상 문서

| 문서 | 주요 데이터 | 비고 |
| --- | --- | --- |
| 0. 수행 계획서 | 프로젝트, 자산, 목표, 범위, IP 정책 | 대부분 수동 입력, 타 보고서의 기준 데이터 |
| 1. 취약점 진단 및 모의해킹 결과 보고서 | 점검 항목, 취약점 유형·건, 시나리오·단계, 재진단 | 레드팀 제출(도구 결과 수동 정리) |
| 2. 블루팀(와주) 보고서 | 관제 환경, 로그 소스, 테스트 케이스, 탐지 전략, 대응 기록, SCA·클라우드 감시 | 블루팀 제출(와주 결과 수동 정리), 버전 0.5/1.0 |

### 1-3. 자동화 흐름

1. 수집: 팀원이 도구(진단 도구, 와주 대시보드 등)를 직접 사용하고 결과값을 노션 DB에 기록(docs/노션 DB 입력 규격.md). 도구·API 자동 연동은 사용하지 않음. 딸깍이는 현재 미사용이며, 추후 선택 기능(가져오기 플러그인)으로 추가할 수 있게 둠(Q-03)
2. 접수 검사: 제출 즉시 데이터 규칙(R-01\~R-13, R-23\~R-26)을 실행하고 오류는 작성자에게 반환
3. 병합·연결: 제출 데이터를 규격 JSON(본 문서 3장)으로 병합. 와주 경보와 시나리오 단계·취약점 건의 연결은 제출자가 출처 ID로 기재하고, 프로그램은 공격 시각·출발지 IP로 대조만 수행(R-21)
4. 생성: 표·통계는 계산하여 Word 템플릿에 렌더링, 사람이 쓴 서술은 AI가 다듬고 정해진 필드만 AI가 작성(5장)
5. 검증: 6장 규칙으로 전체 검사, 실패 항목은 작성자에게 반환
6. 검토·배포: 검토자 승인 후 버전 부여, DOCX(원본) 생성 후 같은 파일을 PDF로 변환하여 함께 배포. 결과 보고서는 v0.5 / v1.0 / v1.1, 블루팀 보고서는 v0.5 / v1.0

### 1-4. 생성 방식

| 방식 | 의미 | 예시 |
| --- | --- | --- |
| 자동 | 제출 데이터와 계산값을 그대로 표·수치로 렌더링. AI 개입 없음 | 위험도별 건수, 건별 목록, 테스트 케이스 표 |
| AI 작성 | 데이터를 입력으로 AI가 새로 서술. 입력에 없는 사실은 쓰지 않음 | 총평, 조치 확인 방법, 공격 내러티브 요약, 증거 캡션 |
| AI 다듬기 | 사람이 쓴 문장의 문체·길이·용어만 고침. 사실·순서·수치는 바꾸지 않음(5-4) | 취약점 개요, 악용 시나리오, 공격 설명, 대표 건과 다른 점 |
| 수동 | 작성자가 직접 입력·판단 | 목표, 위협 카드, 오탐 판단, 승인 |

## 2. 공통 규칙

### 2-1. ID 형식

| ID | 대상 | 형식 (N = 숫자) | 예시 | 발급 주체 |
| --- | --- | --- | --- | --- |
| A | 자산 | A-NN | A-01 | 수행 계획서 |
| O | 목표 | O-N | O-1 | 수행 계획서 |
| A01~A10 | 진단 항목(OWASP Top 10:2025 범주) | ANN | A05 | OWASP 원문 |
| V | 취약점 유형 | V-NN | V-03 | 결과 보고서(레드팀 제출) |
| V-n | 취약점 건 | V-NN-N | V-03-2 | 결과 보고서(레드팀 제출) |
| S | 시나리오 | SN | S1 | 결과 보고서 |
| STEP | 시나리오 단계 | SN-STEPN | S1-STEP3 | 결과 보고서 |
| D | 탐지 검증 테스트 케이스 | D-NN | D-05 | 블루팀 보고서 |
| F | 탐지 개선 조치(탐지 전략서) | F-NN | F-01 | 블루팀 보고서 |
| P | 취약점 패치 | P-NN | P-03 | 프로그램(노션 R6 순서) |
| E | 증거 | E-NNN | E-012 | 프로그램(노션 내보내기 순서, N-9) |

- ID는 발급 후 변경·재사용 금지. 삭제 시 결번으로 남김
- 여러 팀원이 동시에 제출하므로 발급 방식(담당별 번호대 배정 / 병합 시 자동 발급)은 Q-09에서 결정
- 진단 항목 코드 A01~A10은 자산 ID A-NN과 하이픈 유무로 구분함(A05 = 진단 항목, A-05 = 자산)
- 대표 건: 취약점마다 건 번호 1(V-NN-1)이 대표 건이며, 그 취약점에서 위험도가 가장 높은 건에 1번을 붙임(2026-11-15 결정, R-26)

## 3. 데이터 스키마

- 출처 표기: 제출 = 팀원이 도구 결과에서 옮겨 제출한 값 / 계산 = 프로그램이 다른 필드에서 산출 / AI = AI가 작성 후 검토 / 수동 = 작성자 판단·입력
- v0.2부터 도구·API 자동 수집을 사용하지 않으므로 v0.1의 「자동」은 「제출」 또는 「계산」으로 바뀜
- 필수 표기: ● = 필수, ◐ = 조건부 필수(설명란의 조건), ○ = 선택

### 3-5. finding (취약점, V-NN)

- 같은 원인·같은 조치로 묶는 단위(분류 코드 가이드 1장 5번). 같은 취약점의 건이 공유하는 항목(취약점 유형, 개요, 악용 시나리오, 조치방안)을 한 번만 가짐(N-15)
- 결과 보고서 5장의 5칸 구조: 취약점명(title) · 취약점 유형(owasp\_2025) · 상세내용(finding\_instance) · 악용 시나리오(exploit\_scenario) · 조치방안(remediation)
- CVE(알려진 취약 버전 구성요소)는 구성요소 단위로 묶음: 구성요소·버전 하나 = 취약점 하나, 그 안의 CVE = 건. 유형 A03 Software Supply Chain Failures, CWE-1395 + 각 CVE의 CWE(2026-11-15 결정)

| 필드 | 타입 | 필수 | 출처 | 설명 |
| --- | --- | --- | --- | --- |
| finding\_id | V-NN | ● | 제출 |  |
| title | 문자열 | ● | 수동 | 분류 코드 가이드 2장 권장 이름. 5장·7장 공통 제목(단일 출처, R-07). CVE는 「알려진 취약 버전 구성요소 사용 (구성요소명 버전)」 |
| owasp\_2025 | enum owasp\_2025 | ● | 수동 | 범주 하나(대표 범주) |
| cwe | \[CWE-N\] | ● | 수동 | 가장 직접적인 원인을 앞에 둠 |
| classification | enum classification | ● | 수동 | needs\_check는 검토 목록(R-25) |
| severity | enum severity | ● | 계산 | 건 중 최고 등급 = 대표 건 등급(R-26). 4-2 목록 정렬 기준 |
| overview | 문자열 | ● | 수동 + AI 다듬기 | 어디에서 어떤 이유로 발생하는지 한두 줄 |
| exploit\_scenario | 문자열 | ● | 수동 + AI 다듬기 | 공격자가 할 수 있는 일. 확인한 것과 시도하지 않은 것을 구분, 시도하지 않은 것은 「가능성」으로만 표기 |
| fix\_priority | enum fix\_priority | ◐ | 수동 | v0.5부터 필수. 4-2 「조치 구분」 열 |
| root\_cause | 문자열 | ○ | 수동 | 7-1 근본 원인 묶음 표(같은 문구끼리 묶음, N-1) |
| remediation | {steps\[\], code\_before, code\_after, verify} | ● | 아래 | steps = 수동(+ AI 다듬기), code\_before·code\_after = AI 초안 가능 + 수동 확인 필수, verify = AI 작성(대표 건 재현 과정 기반, N-14) |
| code\_reviewed | 참/거짓 | ● | 수동 | 거짓이면 검토 목록(R-25, N-6) |
| references | \[URL\] | ○ | 수동 | OWASP Cheat Sheet·CWE |

- v0.2의 check\_code, description, risk\_rationale, impact는 삭제함(KISA 제외, 5장 위험 평가 설명·영향 칸 삭제, N-15)

### 4-4. 지표 계산식

| 지표 | 계산 |
| --- | --- |
| 탐지율 | score ≥ 3인 test\_case 수 / outcome이 invalid가 아닌 test\_case 수 |
| 차단율 | outcome = blocked 수 / 유효 test\_case 수 |
| MTTD | latency\_sec 평균(경보 발생 건만) |
| MTTA | triage.ack\_at − 첫 경보 시각 평균 |
| MTTR | triage.resolved\_at − 첫 경보 시각 평균 |
| 오탐률 | triage = false\_positive 수 / 전체 triage 건수 |
| 평균 점수 | outcome이 invalid가 아닌 test\_case의 score 평균, 소수점 한 자리 |
| 개선 전·후 | 개선 전 = 최초 실행 test\_case의 score·outcome. 개선 후 = detection\_fix.retest가 있으면 score\_after·outcome\_after, 없으면 개선 전 값 유지. 위 지표를 두 시점으로 각각 계산 |
| 운영 오탐률 | ops\_stats.false\_positives / ops\_stats.alerts\_total (부록 E) |

## 5. AI 작성 규칙

### 5-1. 공통 규칙

- 문체: 개조식, \~함/\~임/\~됨 종결. \~습니다·\~요 금지
- 입력 JSON에 없는 사실·수치·경로·시각 생성 금지. 근거 부족 시 "\[확인 필요\]" 표기
- 문장마다 근거 ID(V-NN-N, SN-STEPN, D-NN, E-NNN) 1개 이상 괄호 표기
- OWASP 범주는 영문 원문 그대로 표기(예: A05 Injection)
- 다듬기 작업은 사람이 쓴 사실·순서·수치·경로·ID를 바꾸지 않음. 문체·길이·용어만 고침
- CWE는 「CWE-번호」 형식, 취약점명은 분류 코드 가이드 2장 이름 그대로 씀
- 과장 표현 금지: "완전히", "매우 심각", "모든" 등은 근거 수치가 있을 때만 사용
- 마스킹: 비밀번호·토큰·세션 값·개인정보는 입력 단계에서 마스킹된 값만 사용, 원문 복원 시도 금지
- 외부 모델 전송 조건: 「마스킹 완료」가 참인 페이지의 값만 모델 어댑터로 보냄. 거짓이면 어댑터가 호출을 거부하고 검토 목록에 올림(R-11과 같은 기준, 2026-11-15 시연에서 확인)
- 출력은 지정 JSON 형식만 허용, 앞뒤 설명문 금지

### 5-3. 입출력 계약

- 호출 단위: 필드 1종 × 대상 1건(예: V-03의 overview)
- 작업 종류(2026-11-15 결정): 작성(write) = 입력 데이터로 새 문장을 씀(remediation.verify, scenario\_step.narrative, 4-1 총평, evidence.caption, 블루팀 AI 필드). 다듬기(polish) = 사람이 쓴 원문을 고침(overview, exploit\_scenario, poc.explanation, diff, remediation.steps, summary\_memo, good\_practices)
- 다듬기 입력에는 원문(source\_text)을 넣고, 출력에는 바꾼 부분 목록(changes)을 남김. 프로그램은 원문과 결과를 비교해 숫자·ID·경로·URL·코드가 바뀌거나 사라지면 needs\_review로 등록함(R-27)
- 입력: {task, style\_rules, target(해당 객체), context(연결 객체 요약), glossary}
- 출력: {id, field, mode(write / polish), text, cited\_ids\[\], changes\[\](polish만), needs\_review(참/거짓), notes}
- needs\_review가 참이면 v0.5 검토 목록에 자동 등록
- 프롬프트 파일은 필드별로 분리 관리(prompts/finding\_overview.md 등), 버전 번호 부여
- 동일 입력 재생성 시 결과 비교를 위해 temperature 낮게 고정

### 5-4. 다듬기(polish) 단계

- 1차: 필드별 작성·다듬기(5-3 작업 종류)
- 2차: 장 단위로 용어 통일·중복 제거만 수행, 사실 추가 금지
- 3차: 6장 검증 규칙 실행 후 실패 항목만 재생성
- 다듬기에서 사람이 쓴 문장이 이미 규칙을 지키면 그대로 둠(바꿀 이유가 없으면 changes 빈 배열)

- 원칙: 규칙을 모델 안이 아닌 파일에 둠. 어떤 모델을 써도 같은 파일·같은 입출력 형식·같은 검증을 거침

| 파일 | 역할 | 비고 |

- 출력 형식 위반 시 1회 재요청, 재실패 시 needs\_review 등록

- 모델별 특수 지시가 필요하면 진입 파일에만 추가하고 사유 기록

### 5-6. 증거 검토(AI 보조)

- 마스킹: 수동이 기본(Q-06 결정). 작성자가 마스킹 후 evidence.masked = 참 입력
- AI 역할: 스크린샷이 연결된 설명(V-NN-N, SN-STEPN, D-NN)을 뒷받침하는지 판단하고 제안만 함. 이미지 수정·교체·삭제 없음
- 판단 기준: 설명의 핵심 요소(요청·응답, 페이로드, 결과 화면, 경보 내용)가 보이는지, 불필요한 영역이 많은지, 캡션과 일치하는지
- 출력: {evidence\_id, fit: enum(fit, partial, unfit), reason, suggestion}
- fit이 partial 또는 unfit인 증거는 검토 목록에 등록, 최종 판단은 작성자

### 5-7. 분량 규칙 (결과 보고서 5장·7장)

- 기준 분량: 건 30건대 초중반, 취약점 20개 안팎에서 본문 약 90쪽, 부록 포함 100\~115쪽(2026-11-15 추정)
- 대표 건의 스크린샷은 본문에 최대 2장, 나머지는 부록 A
- CVE는 구성요소 단위로 묶음(3-5). 대표 건 상세내용은 CVE 번호·버전·확인 결과 위주로 1쪽 이내
- Low·Info 등급 취약점은 간략형(2026-11-15 결정): 개요 표, 개요 한 줄, 그림 1장만 본문에 두고 요청·응답은 부록 A
- 7-2 코드 예시(code\_before·code\_after)는 코드 수정이 필요한 취약점에만 넣음. 설정 변경은 설정 항목만 씀
