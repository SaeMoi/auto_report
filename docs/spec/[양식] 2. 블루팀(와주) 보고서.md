Nov 16, 2026 · @Kim

- 목적: 와주 관제 환경이 실제 공격을 탐지·대응할 수 있는지 검증하고, 미탐을 개선한 과정과 결과를 기록함
- 채점 기준: SCYTHE PTEF v4 「Graded Outcome Scoring」(0\~5점) 및 「Gap Categorization」(공백 5종)
- 핵심 지표: 개선 전후 탐지율·평균 점수, 탐지·대응 소요 시간(MTTD·MTTR)

- 문체: 보고서 문체 규칙(REPORT_STYLE)을 따름. 설명 칸(5-2 미탐 케이스 분석, 6-1 전략 개요·기술 배경, 9장 사고 요약)은 ST-02a 예외를 적용함

### 3-2. 채점 기준 (PTEF v4 Graded Outcome Scoring)

| 점수 | PTEF 단계 | 원문 정의 | 와주 판정 기준 |
| --- | --- | --- | --- |
| 0 | No Visibility | 텔레메트리 미수집 | 에이전트가 해당 로그를 읽지 않음 |
| 1 | Telemetry Available | 로그는 수집돼 수동 조회 가능, 룰·헌팅 플레이북 없음 | 아카이브·인덱서에만 존재 |
| 2 | Hunt Capable | 헌팅 쿼리·플레이북으로 발견 가능, 자동 경보 없음 | 디코더로 필드 추출, 대시보드 쿼리를 문서화함 |
| 3 | Alert Generated | 자동 탐지 룰이 경보 생성 | 룰 매칭, 경보 레벨 이상 기록 |
| 4 | Alert Triaged | 분석가가 정탐 판단 후 기한 내 에스컬레이션 | 블루팀이 경보를 확인·판단한 시각 기록 |
| 5 | Full Response | 탐지부터 봉쇄·조치까지 설계대로 작동 | Active Response 또는 수동 차단·격리 조치 기록 |

- 탐지율: 3점 이상 케이스 비율
- 결과 분류: 차단(Blocked) / 탐지(Detected) / 미탐(NotDetected) — 점수와 별도로 기록
- 점수와 공백 분류를 함께 적음 (예: 「3점 + 프로세스 공백」)

## 5. 공백 분석

### 5-1. 공백 분류 (PTEF v4 Gap Categorization)

| 공백 | 정의 | 와주 예시 | 조치 방향 | 건수 |
| --- | --- | --- | --- | --- |
| 가시성 (Visibility) | 필요한 텔레메트리 미수집 | 앱 로그 localfile 미등록, 디코더 없어 필드 미추출 | 로그 수집·디코더 추가 | \[ \] |
| 탐지 로직 (Detection Logic) | 로그는 있으나 탐지 룰 없음 | IDOR 탐지 룰 없음 | 커스텀 룰 작성 | \[ \] |
| 경보 억제 (Alert Suppression) | 룰이 있었으나 오탐 때문에 억제·비활성화 | 룰 level 0 처리, 무시 규칙 포함 | 정밀한 룰로 재작성 | \[ \] |
| 프로세스 (Process) | 경보는 발생했으나 대응하지 않음 | 낮은 레벨로 아무도 미확인 | 레벨 조정, 알림·절차 보완 | \[ \] |
| 적시성 (Timeliness) | 탐지했으나 기대 시간 내 미탐지 | 일일 점검 쿼리로만 발견 | 실시간 룰·자동 대응 | \[ \] |
| 검증 무효 (자체) | 테스트용 IP 허용 등 훈련 조건으로 판단 불가 | 보안그룹·와주 예외에 테스터 IP 등록 | 조건 해제 후 재시험 | \[ \] |

### 5-2. 미탐 케이스별 분석

케이스마다 다음 세 가지를 1\~2문장씩 씀.

1. 어떤 텔레메트리(로그)가 생성됐어야 하는가
2. 해당 로그를 수집하고 있었는가 (2-2 로그 소스 목록 대조)
3. 해당 기법과 변형까지 탐지하려면 어떤 룰이 필요한가
