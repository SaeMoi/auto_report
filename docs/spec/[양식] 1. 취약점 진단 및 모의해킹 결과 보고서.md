## 1. 개요

### 1-1. 진단 목적

&#91;2\~3문장. 왜 진단했는지, 무엇을 확인하려 했는지(개별 취약점, 연계 공격 가능성, 탐지 연계)를 「~함」으로 씀\]

예: sesacedu.store 서비스와 관리자 구역의 웹 취약점을 OWASP Top 10:2025 기준으로 점검함. 발견한 취약점을 엮어 관리자 권한 탈취와 내부 DB 접근이 가능한지 시나리오로 확인함. 공격 단계마다 남는 흔적을 블루팀 탐지 검증에 넘김

## 3. 위험도 평가 기준 및 적용 결과

### 3-1. 위험도 평가 기준

- 위험도 등급은 점검자가 판단하여 기록하고, CVSS 3.1 기본 점수를 판단 근거로 함께 적음
- 점수와 등급 구간이 맞지 않는 건은 검토 목록에 올려 다시 확인함(값은 바꾸지 않음)
- 건별 CVSS 벡터는 부록 C에 수록함

| 등급 | CVSS 점수 | 판단 예시 |
| --- | --- | --- |
| Critical | 9.0 \~ 10.0 | 인증 없이 원격 명령 실행, 전체 DB 탈취 |
| High | 7.0 \~ 8.9 | 다른 사용자의 개인정보 조회, 관리자 기능 접근 |
| Medium | 4.0 \~ 6.9 | 사용자 상호작용이 필요한 XSS, 제한된 정보 노출 |
| Low | 0.1 \~ 3.9 | 버전 정보 노출, 보안 헤더 누락 |
| Info | - | 직접 악용은 어렵지만 개선을 권고하는 사항 |

- 연계 효과: 단독 등급은 낮지만 Part B 공격 체인에 쓰인 건은 등급을 올리지 않음. 건 목록의 「시나리오 사용」 칸과 6-4 영향 분석에서 따로 설명함

## 5. Part A. 진단 상세 결과

- 서술 순서: 구역 → 대상 → 취약점(V-xx) → 건(V-xx-n)
- 취약점마다 취약점명·취약점 유형·상세내용·악용 시나리오를 쓰고, 조치방안은 7장에 씀
- 같은 취약점이 여러 건이면(예: 파라미터가 다른 Reflected XSS 3건) 유형·악용 시나리오·조치방안은 한 번만 쓰고, 상세내용만 건마다 다른 점을 적음
- 대표 건(V-xx-1)은 위험도가 가장 높은 건으로 두고, 상세내용 소제목 5개(위치·재현 과정·공격 요청·공격 설명·결과)를 모두 씀. 공격 요청이 없는 건(CVE 버전 확인 등)은 「해당 없음」으로 적음
- 나머지 건은 「대표 건과 다른 점」만 쓰고, 재현 증거는 부록 A에 수록함

분량 규칙:

- 대표 건의 스크린샷은 본문에 최대 2장만 넣고, 나머지는 부록 A로 보냄
- Low·Info 등급 취약점은 간략형으로 씀. 개요 표, 개요 한 줄, 그림 1장만 본문에 두고 요청·응답은 부록 A로 보냄
- CVE는 구성요소·버전 하나를 취약점 하나로 묶고, 그 안의 CVE를 건으로 적음. 대표 건 상세내용은 CVE 번호·버전·확인 결과 위주로 1쪽 이내로 씀

문체:

- 개요와 표는 기본 규칙(ST-01\~ST-10)을 따름
- 상세내용과 악용 시나리오는 설명 칸이므로 「~하였음」을 강제하지 않음. 「~함·~됨·~임」과 연결 어미(~하여, ~하고, ~하므로)를 쓸 수 있음(ST-02a)
