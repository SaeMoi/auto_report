## 1. 한 줄 요약

- 팀원은 **도구로 확인한 결과값을 정해진 양식에 정리해 제출**만 하면 됨
- 표·통계·ID는 프로그램이, 설명 문장은 AI가 정해진 문체로 작성하고, 검사를 통과한 결과만 **DOCX(원본) + PDF**로 발행됨

## 2. 대상 보고서

| 문서 | 담당 | 주요 내용 |
| --- | --- | --- |
| 0. 수행 계획서 | 전체 | 범위·자산·목표·진단 항목·수행 규칙·일정 |
| 1. 취약점 진단 및 모의해킹 결과 보고서 | 레드팀 | 2026-11-18부터 두 권으로 나눠 만듦: 취약점 진단 보고서(`-r diag`, 진단 상세·보안 대책·이행 점검)와 모의해킹 보고서(`-r pentest`, 시나리오) |
| 2. 블루팀(와주) 보고서 | 블루팀 | 관제 환경, PTEF 점수 기반 탐지 검증, 공백 분석, 탐지 전략서(ADS), 재검증, 대응 지표 |

- 세 문서는 같은 ID 체계를 공유함. 레드팀의 시나리오 단계(SN-STEPN)·취약점 건(V-NN-N)이 블루팀 테스트 케이스(D-NN)의 출처가 되므로, 레드팀의 공격 시각·출발지 IP가 정확해야 블루팀 결과도 맞음

## 3. 왜 이렇게 하는가

- 작성자마다 문체·용어·표 형식이 달라지는 문제를 없애기 위함
- 어떤 AI 모델을 쓰더라도 같은 규칙 파일(REPORT_STYLE.md)과 같은 검사를 거치므로 결과 문체가 일정하게 유지됨
- 숫자·집계를 사람이 손으로 옮기지 않으므로 요약 표와 상세 내용이 어긋나지 않음

## 4. 전체 흐름

```text
[팀원] 도구 수동 사용 (Burp, 스캐너, 와주 대시보드 등. 딸깍이는 현재 미사용)
   │
   ▼
[팀원] 결과값을 노션 DB에 기록 + 증거 파일 마스킹
   │
   ▼
[프로그램] ① 병합·ID 확인·지표 계산
   │
   ▼
[프로그램] ② 데이터 검사 (형식·누락·참조 오류 → 작성자에게 반환)
   │
   ▼
[AI] ③ 설명 문장 작성 (취약점 설명, 영향, 공격 내러티브, 총평 등)
   │
   ▼
[프로그램] ④ 전체 검사 (문체, 근거 ID, 길이, 마스킹 등 R-01~R-22)
   │
   ▼
[검토자] ⑤ 검토 목록 확인 → 수정 문장은 잠금, 나머지는 재생성
   │
   ▼
[프로그램] ⑥ DOCX 생성 → PDF 변환 → 발행 (v0.5 / v1.0 / v1.1)
```

## 5. 누가 무엇을 하는가

| 구분 | 하는 일 | 하지 않는 일 |
| --- | --- | --- |
| 팀원(작성자) | 도구 사용, 결과값 정리·제출, 증거 마스킹, 판단 항목 입력(목표, 위협 카드, 오탐 판단 등) | 보고서 본문을 Word에서 직접 작성 |
| 프로그램 | 병합, ID·형식 검사, 표·통계·지표 계산, DOCX·PDF 생성 | 사실 판단 |
| AI | 입력 데이터를 근거로 설명 문장 작성, 증거 스크린샷 적합성 의견 제시 | 입력에 없는 사실·수치·경로·시각 작성, 증거 이미지 수정 |
| 검토자 | 검토 목록 확인, 문장 수정·잠금, 발행 승인 | 데이터 없이 문장만 고치기 |

## 6. 팀원이 정리해서 제출할 값

- 아래는 요약임. 필드 전체 목록과 필수 여부는 규격서 3장을 따름

### 6-1. 레드팀: 취약점 진단 (Part A)

| 항목 | 예시 | 비고 |
| --- | --- | --- |
| 취약점명 | Reflected XSS | 취약점(V-NN)마다 한 번 기록. 같은 원인·같은 조치로 묶이는 건들의 공통 이름. 「분류 코드 가이드」 2장 권장 이름 사용 |
| 취약점 유형 | A05 Injection | 취약점마다 한 번. OWASP Top 10:2025 범주 하나 |
| CWE | CWE-79 | 취약점마다 한 번. 「분류 코드 가이드」 2장에서 취약점명과 함께 고름 |
| 개요 | 강의 검색 화면에서 입력값을 그대로 출력해 스크립트가 실행됨 | 취약점마다 한 번. 어디에서 어떤 이유로 발생하는지 한두 줄 |
| 악용 시나리오·조치방안 | 세션 탈취 / 1. 출력 인코딩 … | 취약점마다 한 번. 같은 취약점의 건은 모두 공유 |
| 대상 자산 | A-01 | 수행 계획서의 자산 ID |
| 접근경로 | GET /backend/lectures/{lid}/material/download | 「메서드 /경로」가 들어 있으면 프로그램이 나눔 |
| 위험도·CVSS 3.1 점수·벡터 | Medium (6.5), CVSS:3.1/AV:N/AC:L/... | 작성자가 계산기(https://chandanbn.github.io/cvss/)로 계산·판단해 기록함. 프로그램은 등급·점수·벡터가 서로 맞는지 확인만 하고 바꾸지 않음 |
| 발견 방법 | auto / manual |  |
| 건 본문 | 1. 취약점 개요 표(점검대상·발견 경로·영향도·CVSS Vector), 2. 취약점 상세설명 | 대표 건(V-NN-1)은 소제목 5개(위치, 재현 과정, 공격 요청, 공격 설명, 결과)로 최대한 자세히 서술. 나머지 건은 「대표 건과 다른 점」만. 토큰·비밀번호는 가린 뒤 「마스킹 완료」 체크 |
| 증거 | 스크린샷, 요청·응답 | 「2. 취약점 상세설명」에 서술과 함께 붙임. 증거 번호는 프로그램이 매김 |

- 내용은 사람이 최대한 서술함. 특히 「공격 설명」에는 페이로드가 왜 통하는지(서버가 입력을 어떻게 처리하는지, 무엇이 빠졌는지)를 씀. AI는 문체만 다듬고 내용을 보태지 않음. 작성 예시는 「노션 DB 입력 규격」 부록 B
- 진단 건마다 발견 시각·출발지 IP는 적지 않음. 진단 단계의 출발지 IP는 문서 정보의 「수행 조건」 표에 한 번만 적음

### 6-4. 블루팀: 탐지 검증 (공격 중·후)

| 항목 | 예시 | 비고 |
| --- | --- | --- |
| 테스트 케이스 ID와 출처 | D-01 ← S1-STEP2 / V-03-2 / ATT&CK 모사 | 시나리오 단계·취약점 건·서버 레벨 모사 중 하나와 연결. 취약점 건 출처는 블루팀이 상세설명대로 다시 공격하고 그 시각·IP를 기록 |
| 수행 내용(변형) | SQL 인젝션 시도 |  |
| 경보 | rule.id, level, agent, 경보 시각 | 와주에서 확인한 값을 옮겨 적음 |
| 결과 분류 | blocked / detected / not_detected / invalid | 테스트용 IP 허용으로 판단 불가하면 invalid(검증 무효) |
| PTEF 점수 | 0~5 | 4~5는 대응 기록 필요 |
| 공백 유형 | visibility, detection_logic, alert_suppression, process, timeliness | 미탐이거나 점수 3 미만이면 필수 |
| 대응 기록 | 확인 시각, 정탐·오탐, 조치, 조치 완료 시각, 담당 | MTTA·MTTR 계산에 사용 |
| 증거 | 경보 JSON, 대시보드 화면 | 페이지 본문에 서술과 함께 붙임. 증거 번호는 프로그램이 매김 |

- 수동 입력으로 바뀌면서 경보 시각·rule.id와 단계 연결은 사람이 옮겨야 함. 오류가 가장 많이 나는 부분이므로 시각을 초 단위까지 정확히 적을 것

### 6-5. 블루팀: 개선·재검증·기타

| 항목 | 예시 | 보고서 위치 |
| --- | --- | --- |
| 탐지 전략서(룰 1건당 1건) | F-01: 목표, 분류, 사각지대·가정, 오탐, 우선순위(level과 근거), 대응, 디코더·룰 파일 | 6-1 |
| 오탐 튜닝 | 룰, 관찰 기간, 경보 건수, 오탐 건수, 원인, 조치 | 6-2 |
| 재검증 | D-ID, F-ID, 점수 전→후, 결과 분류 전→후, 재검증 일시, 변형 공격 결과 | 7 |
| 침해사고 타임라인(대표 1건) | 시각, 출처(경보/로그), 공격자 행위, 방어 측 활동, IOC | 9 |
| SCA·취약 패키지 | 자산 ID, 정책, 점수 전→후, 주요 미통과 항목, 취약 패키지 건수 전→후 | 10-1 |
| 클라우드 감시 | 보안그룹·IAM·콘솔 로그인별 수집 여부, 탐지 룰 | 10-2 |
| 개선 과제 | 과제, 관련 공백, 담당, 기한, 상태 | 11-3 |
| 운영 통계 | 기간별 경보 건수, 많이 발생한 룰 Top 10, 오탐률 | 부록 E |
| 원본 파일 | 커스텀 디코더·룰 XML, 주요 경보 JSON | 부록 A·B |

- 전략 개요·기술 배경, 미탐 케이스 분석, 요약·교훈 문장은 AI가 위 값을 근거로 초안을 쓰고 블루팀이 검토함
- 탐지율, 평균 점수, 공백 유형별 건수, MTTD·MTTA·MTTR·오탐률, 개선 전·후 비교, ATT&CK 커버리지 그림은 프로그램이 계산·생성함. 직접 계산해서 적지 않음

### 6-6. 기록 위치와 분류

- 모든 값은 노션에 기록함. DB·페이지 목록과 속성은 「노션 DB 입력 규격.md」 v0.2를 따름

| 묶음 | DB·페이지 |
| --- | --- |
| 공통 | 문서 정보, 자산, 목표 |
| 레드팀 | 웹 서비스 취약점 목록(취약점 건), 취약점, 진단 항목 판정(OWASP 10개), 시나리오, 시나리오 단계, 취약점 패치, 재진단 |
| 블루팀 | 관제 환경, 로그 소스, 와주 모듈, 탐지 검증 테스트 케이스, 탐지 전략서, 침해사고 분석, SCA 결과, 클라우드 감시, 개선 과제, 운영 통계 |

- 증거는 별도 DB 없이, 증거가 뒷받침하는 페이지 본문에 서술과 함께 이미지·코드 블록으로 붙임. 증거 번호와 증거 목록은 프로그램이 내보내기에서 자동으로 만듦
- 취약점 유형(OWASP)·취약점명·CWE는 「분류 코드 가이드.md」로 정하고, 헷갈리면 가이드 6장 프롬프트로 AI에 점검을 맡긴 뒤 「분류 확정」을 확인 필요로 둠

### 6-7. 직접 입력하지 않는 값

- 아래 값은 프로그램이 계산함. 노션에 칸을 따로 만들어 손으로 적지 않음
- 손으로 적은 값은 계산값과 어긋나기 쉽고, 어긋나면 요약 표와 상세 내용이 달라짐(R-06, R-08, R-09 오류)

| 값 | 계산 근거 |
| --- | --- |
| 취약점 위험도(V-NN 최고 등급) | 같은 취약점 건들의 위험도 |
| 목표 달성 소요 시간 | 시나리오 단계의 첫 단계 시작 ~ 달성 단계 종료 |
| 시나리오 단계의 실제 탐지 | 블루팀 테스트 케이스의 출처 ID 역참조 |
| 탐지 소요 시간, MTTD·MTTA·MTTR, 탐지율, 평균 점수, 오탐률 | 테스트 케이스의 시각·점수·판단(규격서 4-4) |
| 재검증 전 점수·결과 | 테스트 케이스 |
| 건수·소계·합계, 출처별 테스트 건수, 공백 유형별 건수 | 각 DB 집계 |
| 증거 번호(E-NNN)와 증거 목록(종류, 파일 경로) | 페이지 본문의 이미지·코드 블록 |

## 7. 입력 규칙 (꼭 지킬 것)

| 규칙 | 내용 |
| --- | --- |
| 시각 | ISO 8601, 초 단위, KST 명시. 예: 2026-11-20T14:03:12+09:00 |
| ID | 한 번 발급한 ID는 바꾸거나 재사용하지 않음. 삭제 시 결번으로 둠 |
| 취약점 유형(OWASP) | Top 10:2025 코드 + 영문 원문 그대로(예: A05 Injection) |
| CWE | 「CWE-번호」 형식. 여러 개면 쉼표로 구분하고 직접적인 원인을 앞에 둠 |
| 민감정보 | 비밀번호·토큰·세션·개인정보는 마스킹한 값만 입력. 예: hong\*\*\*@\*\*\*.com |
| 증거 | 마스킹을 마친 뒤 페이지 본문에 붙이고, 그 페이지의 「마스킹 완료」를 체크. 체크하지 않은 페이지의 증거는 보고서에 들어가지 않음 |
| 허용 값 | 위험도·결과·상태 등은 규격서 2-3 열거형 값만 사용 |
| 근거 없는 값 | 모르는 값은 비워 두거나 [확인 필요]로 표기. 추정값 입력 금지 |

## 8. 결과물과 수정 규칙

- 발행 형식: **DOCX가 원본**이고, PDF는 같은 DOCX를 변환해 만들므로 두 파일 모양이 같음
- 내용 수정은 **입력 데이터 또는 검토 단계의 문장 잠금**으로 함. DOCX를 직접 고치면 다음 생성 때 사라짐
- DOCX 직접 수정은 발행 직전 마무리(쪽 나눔 조정 등)에만 허용함

| 버전 | 시점 | 발행 조건 |
| --- | --- | --- |
| v0.5 | 진단 완료 후 중간본 | 오류 0건 |
| v1.0 | 모의해킹 완료 후 최종본 | 오류 0건 + 경고 0건(또는 검토자 승인) |
| v1.1 | 재진단 후 | retest 데이터 포함 |

- 블루팀 보고서는 재진단 단계가 없으므로 v0.5(중간본)·v1.0(최종본)만 사용함(2026-11-12 결정)

## 9. AI가 쓰는 문장의 규칙

- 개조식, ~함/~임/~됨 종결. ~습니다·~요 사용 안 함
- 문장마다 근거 ID(V-NN-N, SN-STEPN, D-NN, E-NNN)를 괄호로 표기
- 입력에 없는 사실은 쓰지 않고 [확인 필요]로 남김
- 위 규칙에 어긋나면 프로그램이 자동으로 걸러 재작성하거나 검토 목록에 올림
- 규칙 원본은 docs/REPORT_STYLE.md 하나뿐이며, 규칙 변경은 이 파일에서만 함

## 11. 질문 예상 리스트

- **Word로 직접 쓰면 안 되나?** 직접 쓴 내용은 검사와 집계에 반영되지 않고 다음 생성 때 사라짐. 값은 노션에 기록할 것
- **AI가 틀린 내용을 쓰면?** AI는 제출된 값만 근거로 쓰고, 검사에서 걸리거나 검토자가 고친 문장은 잠금 처리되어 다시 바뀌지 않음
- **어떤 AI를 쓰나?** Claude, Codex를 병행 예정이며 어느 모델이든 같은 규칙·같은 검사를 거침
- **값을 잘못 냈으면?** 제출 즉시 데이터 검사 결과가 돌아오므로 해당 항목만 고쳐 다시 제출하면 됨
