# 분류 코드 가이드 v0.3

- 기준일: 2026-11-15
- 용도: 취약점을 노션 DB에 기록할 때 취약점 유형(OWASP Top 10:2025 범주)·취약점명·CWE를 정하는 기준. 팀원이 직접 참고하거나, 7장 프롬프트와 함께 AI에 넣어 분류를 점검함
- 기준 자료: [OWASP Top 10:2025](https://top10.owasp.org/2025/), [MITRE CWE](https://cwe.mitre.org/)
- 우선순위: 규격서 > 본 문서. 범주와 취약점명의 연결은 [양식] 1. 결과 보고서 2-2 표와 같게 유지함
- v0.3 변경(2026-11-15): KISA 코드 제외. 분류는 「OWASP 범주 → 취약점명 → CWE」 세 단계로만 함

## 1. 분류 순서

1. **원인으로 분류함.** 결과(계정 탈취, 정보 유출)가 아니라 「무엇이 빠져서 가능했는가」로 정함
2. **취약점 유형은 OWASP 범주 하나를 고름(필수).** 여러 범주에 걸치면 원인에 가장 가까운 대표 범주 하나만 씀
3. **취약점명은 2장의 권장 이름에서 고름.** 목록에 없으면 같은 형식(일반적으로 쓰는 영문 약어 또는 짧은 한국어)으로 새로 쓰고 「분류 확정」을 확인 필요로 둠
4. **CWE는 취약점명 옆의 CWE를 기본으로 쓰고**, 더 정확한 CWE가 있으면 그것을 씀. 여러 개면 쉼표로 구분하고 가장 직접적인 원인을 앞에 둠
5. **취약점(V-NN)으로 묶는 기준은 「같은 원인 · 같은 조치」임.** 예: 파라미터만 다른 Reflected XSS 3건은 V-NN 하나의 건 3개. 원인이나 조치가 다르면 취약점을 나눔
6. 판단이 어려우면 후보를 적고 「분류 확정」을 확인 필요로 둠. 검토자가 확정함

## 3. 헷갈리는 구분

| 상황 | 분류 | 구분 기준 |
| --- | --- | --- |
| 로그인 없이 기능이나 토큰을 얻음 | A07 인증 누락 | 인증 자체가 없거나 우회됨 |
| 로그인은 했지만 남의 데이터에 접근함 | A01 IDOR | 인증은 정상, 객체 소유권 검증이 없음 |
| 로그인은 했지만 권한 밖 기능을 씀 | A01 권한 검증 누락 | 객체가 아니라 기능 단위 |
| 서버가 내가 준 URL로 요청함 | A01 SSRF | 파일 경로를 조작해 파일을 받으면 경로 조작 |
| 에러 화면에 스택 트레이스 노출 | A10 오류 메시지 정보 노출 | 에러가 아닌 응답·문서·주석의 정보는 A02 과도한 정보 노출 |
| 업로드한 파일이 서버에서 실행됨 | A06 악성 파일 업로드 | 확장자·실행 통제가 설계에서 빠짐 |
| 오래된 버전 정보가 보임 | A02 또는 A03 | 버전 노출만이면 A02, 그 버전의 알려진 취약점을 실제로 확인했으면 A03 |
| JWT 관련 문제 | A04 또는 A07 | 키·알고리즘이 약하면 A04, 만료·서명 검증이 빠졌으면 A07 |
| 반복 요청 무제한 | A07 또는 A06 | 로그인·OTP면 A07 무차별 대입, 쿠폰·포인트 등 업무 기능이면 A06 |
| 공격이 로그·알림에 남지 않음 | A09 | 레드팀 단독보다 블루팀 탐지 결과와 함께 판단 |

## 5. 노션 DB 기록 항목

- 분류는 취약점 건(R1)이 아니라 취약점(R2) 페이지에 한 번만 기록함. 속성 정의는 「노션 DB 입력 규격.md」 R2를 따름
- 취약점 유형(OWASP, 필수), 취약점명(제목), CWE(필수), 분류 확정(확정 / 확인 필요)

## 6. AI 점검용 프롬프트

- 사용법: 아래 코드 블록 전체 + 본 문서 전체 + 점검할 노션 페이지 내용(마스킹 후)을 AI에 붙여넣음
- AI 결과는 제안이며, 최종 분류는 작성자와 검토자가 확정함

```text
너는 웹 취약점 분류 검토자다. 함께 붙여넣은 「분류 코드 가이드」만 기준으로 사용한다.

[작업]
아래 취약점 노트를 읽고 분류와 서술 누락을 점검한다.

[규칙]
1. 취약점 유형은 가이드 2장의 OWASP Top 10:2025 범주(A01~A10) 중 하나만 고르고, 「코드 + 영문 원문」으로 쓴다.
2. 취약점명은 가이드 2장의 권장 이름에서 고른다. 맞는 것이 없으면 새 이름을 제안하고 그 이유를 적는다.
3. CWE는 「CWE-번호」 형식으로 쓴다. 가이드에 없는 번호를 제안할 때는 CWE 이름을 함께 적는다.
4. 결과가 아니라 원인으로 분류한다(가이드 1장). 원인이나 조치가 다른 건이 섞여 있으면 취약점을 나누라고 제안한다.
5. 근거는 노트에 적힌 사실과 가이드의 문구로만 든다. 노트에 없는 사실은 추측하지 않고 [확인 필요]로 적는다.
6. 노트에 비밀번호·토큰·세션 값·개인정보가 마스킹되지 않은 채 있으면 위치를 지적한다.
7. 문체는 개조식, ~함/~임/~됨 종결.

[출력 형식]
| 항목 | 제안 | 근거 |
| 취약점 유형 (OWASP) | | |
| 대안 범주(있으면) | | 왜 대안인지, 무엇을 확인하면 정해지는지 |
| 취약점명 | | |
| CWE | | |
| 취약점 분리 제안 | | |
| 확신도 | 높음 / 중간 / 낮음 | |

[누락 점검] 아래 값이 노트에 있는지 표시한다.
- 취약점(R2): 취약점명, 취약점 ID, 취약점 유형, CWE, 본문 제목 「개요」(한두 줄)·「악용 시나리오」·「조치방안」
- 건(R1): 건 ID, 취약점 ID, 자산 ID, 접근경로(메서드 /경로), 위험도, 개요 표의 영향도(등급 (점수) — 근거)와 CVSS Vector, 발견 방법, 의도적 취약점 여부, 조치 상태, 마스킹 완료 여부
- 대표 건 「2. 취약점 상세설명」의 소제목 5개: 위치, 재현 과정, 공격 요청, 공격 설명, 결과. 대표 건이 아니면 「대표 건과 다른 점」
- 「공격 설명」에 페이로드가 왜 통하는지(서버가 입력을 어떻게 처리하는지)가 적혀 있는지
[마스킹 점검] 마스킹되지 않은 값의 위치

[노트]
```
