### 0-3. 본문 표 규칙

- 한 페이지에 여러 줄이 필요한 값(경보 목록, 개정 이력 등)은 본문에 지정한 제목 아래 표로 기록함
- 표의 머리행 문구와 열 순서를 바꾸지 않음. 프로그램은 제목 → 머리행으로 표를 찾음
- 해당 사항이 없으면 표를 지우지 말고 머리행만 남김

본문 제목:

- **작성자** — 표 `| 이름 | 역할 | 담당 영역 | 담당 장 | 연락처 |` → authors. 「담당 영역」은 선택(결과 보고서 1-4 진단 인력)
- **개정 이력** — 표 `| 버전 | 날짜 | 작성자 | 변경 내용 |` → revisions
- **요약 메모** — 수행 계획서 0-1용 자유 서술(AI는 문장 다듬기만 함)
- **수행 조건** — 결과 보고서 1-5용 표 `| 단계 | 출발지 IP | IP 허용 | Active Response | 시작 조건 |`. 진단(Part A) 출발지 IP는 건별이 아니라 여기에 기록함
- **잘 된 보안 사항 메모** — 결과 보고서 4-4용 표 `| 항목 | 효과 | 근거 ID |`. 근거 ID 필수
- **진단 목적** (선택, v0.3) — 결과 보고서 1-1 자유 서술. 비우면 보고서에 [확인 필요]로 나옴
- **사용 도구** (선택, v0.3) — 목록. 도구 이름과 버전 → 결과 보고서 1-5·5-1, 수행 계획서 0-11
- **테스트 계정** (선택, v0.3) — 표 `| 계정 | 권한 |` → 결과 보고서 1-5, 수행 계획서 0-6. 비밀번호는 적지 않음
- **일정** (선택, v0.3) — 표 `| 단계 | 기간 | 내용 |` → 결과 보고서 1-3, 수행 계획서 0-9. 비우면 수행 시작일~종료일 한 줄로 나옴
- **네트워크 구성** (선택, v0.3) — 인프라 구성도 그림과 그 아래 캡션 한 줄. 수행 계획서 0-4와 결과 보고서 1-2에 그림으로 들어감. 문서 정보 페이지 중 한 곳에만 넣어도 됨. 그림에 인스턴스 ID·AMI ID·키 페어·IAM 이름이 보이지 않게 가린 뒤 넣음(이 그림은 마스킹 확인 없이 그대로 실림)
- 수행 계획서 페이지에만 쓰는 본문 장 (선택, v0.3): **수행 개요**, **범위**, **수행 규칙**, **디컨플릭션**, **비상 연락**, **네트워크 구성**, **승인**. 표·목록을 그대로 수행 계획서 해당 장에 옮김(AI가 고치지 않음)

## 2. 레드팀 DB

### R1. 취약점 건

- 기존 「웹 서비스 취약점 목록」 DB를 그대로 씀. 페이지 1개 = 취약점 건 1개(V-NN-N)
- 팀이 쓰던 본문 구조(개요 표 → 상세설명)를 쓰고, 악용 시나리오·조치방안은 R2 「취약점」 본문에 취약점마다 한 번만 씀(2026-11-15 피드백 반영)
- 같은 취약점의 건이 여러 개면(예: 파라미터가 다른 Reflected XSS 3건) 건 번호 1(V-NN-1)을 대표 건으로 보고 재현 과정 전체를 쓰며, 나머지 건은 대표 건과 다른 점만 씀
- 올리는 건은 모두 검증을 마친 것으로 봄(verified\_manually = 참 고정, 2026-11-15 결정)
- 취약점 유형(OWASP)·CWE는 건마다 적지 않고 R2 「취약점」에 한 번만 적음

| 속성 | 노션 타입 | 선택지·형식 | 필수 | 규격서 필드 | 비고 |
| --- | --- | --- | --- | --- | --- |
| 건 제목 | 제목 | 자유 | ● | — | 기존 「취약점명」 속성. 건 목록 표의 위치 설명에 참고. 보고서의 취약점명은 R2에서 가져옴 |
| 건 ID | 텍스트 | V-NN-N | ● | instance\_id | 발급 방식은 Q-09 |

| 팀 분류 | 선택 | 정보노출, AUTH, XSS, FILE, SQL, RCE | ○ | — | 기존 「취약점 유형」 속성 이름 변경(보고서의 「취약점 유형」=OWASP와 혼동 방지). 팀 내부 분류, 보고서에는 미사용 |
| 발견 방법 | 선택 | 수동, 자동 도구 | ● | discovery | 비우면 수동으로 봄 |
| 의도적 취약점 | 체크박스 | 참/거짓 | ● | intentional | 워게임용으로 심은 취약점 |
| 조치 상태 | 선택 | 미조치, 조치 완료, 부분 조치, 재검증 완료 | ● | status |  |
| 마스킹 완료 | 체크박스 | 참/거짓 | ● | evidence.masked | 4장 |

| 작성자 | 사람 | — | ● | authors | 기존 유지 |

- 발견 시각·출발지 IP는 건마다 기록하지 않음(2026-11-15 결정). 진단 단계는 테스터 IP를 허용한 상태라 건별 탐지 대조의 실익이 없음

- 내용은 사람이 최대한 서술하며 작성함(2026-11-15 결정). AI는 문체·길이·용어만 다듬고 사실을 보태지 않음(R-15). 표·건수·목록은 프로그램이 만듦
- 대표 건은 건 번호 1(V-NN-1)로 봄. 대표 건을 바꾸려면 건 번호를 바꿈
- 작성 예시는 부록 B 참조

- 「3. 악용 시나리오」·「4. 조치방안」은 R2 본문으로 옮김. 기존 페이지에 남아 있어도 프로그램은 읽지 않음
- 「조치 확인 방법」 제목은 두지 않음(2026-11-15 결정). 7-2 확인 방법과 재진단(R7) 기준은 「2. 취약점 상세설명」의 재현 과정을 다시 수행해 재현되지 않는지로 정하며, AI가 상세설명을 바탕으로 문장을 쓰고 검토 목록에 올림

- 기존 「취약점명」·「취약점 설명」 행은 R2로 옮김(취약점명 → R2 제목, 취약점 설명 → R2 「개요」). 남아 있어도 읽지 않음

CVSS 확인 (경고만, 2026-11-15 결정):

- 점수·벡터는 작성자가 계산기(https://chandanbn.github.io/cvss/)로 계산해 기록함
- 프로그램은 아래를 확인만 하고 검토 목록에 올림. 위험도·점수를 바꾸거나 발행을 막지 않음
  - 점수가 「위험도」 등급 구간과 맞지 않음(예: 6.5인데 High)
  - 벡터로 다시 계산한 점수가 적힌 점수와 다름
  - 점수 또는 벡터가 비어 있음

### R2. 취약점

- 페이지 1개 = 취약점 1개(V-NN, 같은 원인·같은 조치로 묶는 단위. 예: Reflected XSS). 5장·7장 공통 제목의 단일 출처(R-07)이며, 7장 보안 대책의 사람 입력 값을 담음
- 같은 취약점의 건(R1)이 공유하는 항목(취약점 유형, 개요, 악용 시나리오, 조치방안)을 이곳에 한 번만 적음(2026-11-15 피드백 반영)

본문 제목 (제목 문구 고정):

- **개요** — 어디에서 어떤 이유로 이 취약점이 발생하는지 한두 줄 → finding.overview(5장 개요)
- **악용 시나리오** — 이 취약점으로 공격자가 할 수 있는 일을 순서대로 최대한 서술함. 실제로 확인한 것과 시도하지 않은 것을 나눠 씀 → 5장 악용 시나리오. 시도하지 않은 것은 AI가 「가능성」으로만 다듬음
- **원인** (선택, v0.3) — 7-2 「원인」 한 줄 → remediation.cause
- **조치방안** — 번호 목록 → 7-2 대책(remediation.steps). 같은 취약점의 모든 건에 공통 적용
- **설정 변경** (선택, v0.3) — 코드가 아니라 설정으로 고치는 경우 한두 줄 → remediation.config\_change
- **취약한 코드** — 코드 블록 → remediation.code\_before
- **수정한 코드** — 코드 블록 → remediation.code\_after
- 두 코드는 AI가 초안을 만들 수 있으나 반드시 사람이 확인함(규격서 3-5 「코드는 수동 검토 필수」)

### R3. 진단 항목 판정

- 범주 안에서 점검한 취약점명·CWE는 판정하지 않고, 결과 보고서 2-2 표의 「주요 점검 취약점」 열과 부록 B로 보여 줌

- 재진단 중 새로 발견한 취약점은 이 DB가 아니라 R1에 새 건 ID로 등록함

### B4. 탐지 검증 테스트 케이스

- 실행 전에 「계획」 상태로 먼저 만들고(테스트 계획 표, 부록 D), 실행 후 「실행 완료」로 바꾸며 결과를 채움
- 레드팀 단계·건과의 연결은 이 DB의 「출처 ID」로만 기록함(블루팀 → 레드팀 한 방향)
- 출처가 취약점 건이면 블루팀이 R1 「2. 취약점 상세설명」의 재현 과정을 다시 수행하고, 그 실행 시각·출발지 IP를 기록함. 시각·IP 대조(R-21)는 출처가 시나리오 단계인 테스트에만 적용함

| --- | --- | --- | --- | --- | --- |

- 「검증 무효」는 테스트용 IP 허용 등으로 판단할 수 없는 경우에만 사용하고 점수를 비움

## 4. 증거 기록 방법

- 증거는 별도 DB를 만들지 않음. 증거가 뒷받침하는 페이지 본문에 서술과 함께 스크린샷·코드 블록으로 붙임(취약점 건은 「2. 취약점 상세설명」)
- 증거 번호(E-NNN)는 사람이 적지 않음. 프로그램이 노션 내보내기에서 증거를 찾아 번호를 매기고 증거 목록(규격서 3-11 evidence)을 만듦(2026-11-15 결정)

### 4-1. 붙이는 방법

| 증거 종류 | 붙이는 방법 |
| --- | --- |

2. 취약점 상세설명

- **위치** — GET /lectures/search, 파라미터 keyword, 비회원도 접근 가능
- **재현 과정** — 1. 검색창에 `<script>alert(1)</script>` 입력 2. 결과 페이지에서 알림창이 뜨는지 확인 3. 같은 값을 URL에 넣은 링크를 다른 브라우저에서 열어 재현
- **공격 요청** — 코드 블록: `GET /lectures/search?keyword=%3Cscript%3Ealert(1)%3C%2Fscript%3E`
- **공격 설명** — 서버는 keyword 값을 결과 페이지의 「"…" 검색 결과」 문구에 그대로 넣어 HTML로 응답함. `<`, `>`가 `&lt;`, `&gt;`로 바뀌지 않아 브라우저가 입력값을 문자가 아닌 script 태그로 해석함. 페이로드의 `<script>` 태그가 새 스크립트 블록을 열고, `alert(1)`은 실행 여부만 보여 주는 무해한 확인용 코드임
- **결과** — 응답 HTML에 `<h2>"<script>alert(1)</script>" 검색 결과</h2>`가 인코딩 없이 들어 있음(코드 블록), 알림창 스크린샷 첨부. 비회원 상태에서도 링크만으로 실행됨을 확인함
